## 2. Root Clutter Assessment

### Current state

The root directory has **22 visible files**. For a Rust workspace, the expected root files are: `Cargo.toml`, `Cargo.lock`, `.gitignore`, and project documentation. Nornir has those plus 11 deploy scripts and 1 generator script.

### Impact

When an LLM runs `ls` at the workspace root, it sees:
```
AUDIT_GUIDE.md               deploy_daemons.py        deploy_tools.py
CLAUDE.md                    deploy_dispatchers.py     deploy_watchers.py
Cargo.lock                   deploy_gates.py           deploy_writers.py
Cargo.toml                   deploy_hooks.py           generate_writer.py
MANDATORY_READ_BEFORE_CODING.md  deploy_interceptors.py  NORNIR_BUILDING_AND_COMPOSITION.md
NORNIR_NAMING.md             deploy_rewriters.py       NORNIR_ORGANIZATION.md
QUICKSTART.md                deploy_senders.py
```

The deploy scripts dominate the listing. An LLM sees 12 Python scripts interleaved with documentation and thinks "this project has a lot of build automation at the root." The scripts dilute the signal from the documentation files, which are far more important for a new session to discover.

### The documentation files are correctly placed

CLAUDE.md, MANDATORY_READ_BEFORE_CODING.md, NORNIR_NAMING.md, NORNIR_ORGANIZATION.md, NORNIR_BUILDING_AND_COMPOSITION.md, and QUICKSTART.md all belong at the root. They are the first things an LLM should read. Moving them to a `docs/` directory would add one layer of indirection between the session and the instructions it needs.

### AUDIT_GUIDE.md is misplaced

AUDIT_GUIDE.md is a reference document for auditors, not a session primer. It generates audit reports that go into `audit/`. It should live in `audit/AUDIT_GUIDE.md` alongside the reports it produces. This colocation makes the relationship between the guide and its outputs discoverable.

### PLAN.md is a ghost

NORNIR_ORGANIZATION.md references `PLAN.md` in the directory map on line 64, but this file does not exist. The actual development plan is `plans/IMPROVEMENT_PLAN.md`. This is a stale reference that will confuse any session that reads the organization doc and then looks for PLAN.md.

## 3. Deploy Script Organization

### Current state

11 deploy scripts and 1 generator script live at the workspace root. All deploy scripts follow an identical four-function pattern:
1. `build_{category}()` -- runs `cargo build --release -p crate1 -p crate2 ...`
2. `ensure_symlinks()` -- creates/updates symlinks in `~/.ai/tools/bin/`
3. `verify()` -- runs each binary with a smoke test
4. `__main__` -- calls build, symlink, verify in sequence

The scripts differ only in:
- The crate list
- The verify command and accepted exit codes
- Log message strings

### Structural duplication

The 10 non-gate deploy scripts (everything except `deploy_gates.py`) are nearly identical. Diff analysis confirms: the scripts are template copies where only the category name, crate list, and verify method differ. Total: ~1,081 lines across 10 scripts, of which approximately ~900 are structurally duplicated boilerplate.

`deploy_gates.py` is unique -- it handles both CLI builds (cargo) and PyO3 gate builds (maturin + wheel extraction). It is the only deploy script that justifiably has custom logic.

### Assessment

**What works:** Each script is self-contained and executable. The invocation `./deploy_hooks.py` is memorable and discoverable. The scripts encode important deployment knowledge (symlink paths, verification commands, crate lists).

**What does not work:**

1. **Root clutter.** 12 Python files at the root obscure the project structure.

2. **Massive duplication.** Adding a new binary category requires copying an existing script and doing find-replace on the category name. An LLM doing this will introduce subtle inconsistencies (different verify commands, different accepted exit codes).

3. **Crate lists are separated from the crates.** To know what `deploy_writers.py` deploys, you must read the script. You cannot see this by looking at the `writers/` directory. The deploy script and its crate directory are not colocated.

4. **No single entry point.** To deploy everything after a schema change, a session must run 11 separate commands. There is no `deploy_all.py` or equivalent.

5. **Six of the eleven scripts deploy exactly one crate.** `deploy_converters.py`, `deploy_rewriters.py`, `deploy_dispatchers.py`, `deploy_watchers.py`, `deploy_interceptors.py`, and `deploy_daemons.py` each have a single-element crate list. These are 100+ lines of boilerplate for a one-item list.

### generate_writer.py

This is a scaffolding tool, not a deploy script. It generates new writer crate source files. Its placement at the root is defensible since it operates at workspace scope, but it would be better colocated with deploy scripts if those move.

## 4. Single-Member Category Directories

### Current state

Six top-level directories contain exactly one crate each:

| Directory | Sole Member | Deploy Script |
|-----------|-------------|---------------|
| `converters/` | `convert_json_to_toml` | `deploy_converters.py` |
| `rewriters/` | `rewrite_compaction_summary` | `deploy_rewriters.py` |
| `dispatchers/` | `split_jsonl_batches` | `deploy_dispatchers.py` |
| `watchers/` | `watch_and_diff_exchange_intercepts` | `deploy_watchers.py` |
| `interceptors/` | `traffic_interceptor_rewriter` | `deploy_interceptors.py` |
| `daemons/` | `record_datagrams` | `deploy_daemons.py` |

Each single-member directory comes with a dedicated deploy script. That is 6 top-level directories and 6 deploy scripts (roughly 640 lines of code) to house 6 binaries.

### Assessment

**The category system is sound in principle.** Verb prefixes map to directories. A `convert_*` binary goes in `converters/`. This is the correct design for a workspace that expects growth.

**The problem is overhead at current scale.** The directory tree shows 6 categories with 1 member each. An LLM looking at `ls` sees `converters/`, `rewriters/`, `dispatchers/`, `watchers/`, `interceptors/`, `daemons/` and reasonably infers these are substantive categories. Opening each one reveals a single crate. The signal-to-noise ratio is poor.

**When growth is speculative, single-member directories mislead.** If `converters/` will have 5 members within a month, the directory earns its place. If `converters/` has had 1 member for its entire existence and no second member is planned, the directory is ceremony.

**Counter-argument: consistency.** Every binary category has a directory. There are no exceptions to remember. An LLM adding a new `convert_*` binary knows exactly where to put it without consulting documentation.

**Verdict:** The consistency argument wins, but only if the deploy script overhead is eliminated. Six dedicated deploy scripts for six single-crate directories is not justified. The directories can stay if a unified deploy mechanism replaces the per-category scripts (see plan).

## 5. The cli/ Directory: Mixed Category

### Current state

`cli/` contains 10 crates:
- 8 `check_*` binaries (CLI validation tools)
- 2 specialist tools (`saga_cli`, `syn_cli`)

The `check_*` binaries are deployed by `deploy_gates.py`. The specialist tools are deployed by `deploy_tools.py`.

### Assessment

**The `check_*` binaries belong together.** They follow a uniform pattern, share the same deploy script, and use the same capability crate (`io_check`).

**The specialist tools do not belong in `cli/`.** `saga_cli` and `syn_cli` are not CLI validation tools. They are complex quality pipeline binaries. Their presence in `cli/` alongside `check_*` binaries creates a false equivalence. An LLM seeing `saga_cli` in `cli/` will assume it follows the same pattern as `check_raw_definition` -- it does not.

**The naming exception compounds the confusion.** `saga_cli` produces binary `saga`, and `syn_cli` produces binary `syn`. These are the only crates in the entire workspace where directory name (and package name) do not equal binary name. Putting them in a directory called `cli/` (which implies they are check tools) makes discovery harder.

**What would be clearer:** The specialist tools in their own `tools/` directory, making the `cli/` directory purely for `check_*` binaries. This would make `cli/` perfectly uniform: every member uses `io_check`, is deployed by `deploy_gates.py`, and follows the `check_` naming pattern.

## 6. Core vs. Capability Organization

### Current state

`core/` has 11 crates, `capability/` has 10 crates. The separation encodes Tier 1 (pure, no I/O) vs Tier 2 (may have I/O).

### Assessment

**The physical separation is valuable.** An LLM can tell a crate's tier by its directory. `core/path_core` is pure. `capability/path_verify_io` does I/O. No documentation needed to infer this.

**Naming is almost consistent.** 10 of 11 core crates use the `_core` suffix. The exception:

- `datagram_types` -- sits in `core/`, is pure (defines Datagram/DatagramKind/Priority types), but uses `_types` suffix instead of `_core`. The documented convention says core crates use `_core` suffix, and NORNIR_NAMING.md lists it explicitly under "Core Libraries." This is a naming inconsistency.

**schemas_embedded tier placement is debatable.** `schemas_embedded` sits in `capability/` but performs no I/O at runtime. Its only compile-time behavior is `include_str!()`, which is a compiler directive, not I/O. At runtime, it is a bag of static string constants. It depends only on `schema_core` (a Tier 1 crate). By the purity test, it belongs in `core/`. However, `include_str!()` reads files at compile time, which could be considered an impure dependency on the filesystem. The current placement is defensible but could surprise a session that checks whether "capability" crates perform I/O.

## 7. Workspace Cargo.toml Member Ordering

### Current state

The 87 workspace members in `Cargo.toml` are listed in a seemingly chronological order -- the order they were added. They are not grouped by category, not alphabetized, and not documented with comments.

### Assessment

**The ordering is not discoverable.** To find whether a specific crate is a workspace member, an LLM must scan all 87 lines. To add a new member, there is no obvious insertion point. To verify completeness, there is no way to compare the list against directory contents without manual cross-referencing.

**The lack of category grouping is a missed signal.** The Cargo.toml could reinforce the architecture:

```toml
members = [
    # Tier 1: Core (pure libraries)
    "core/error_core",
    "core/format_core",
    ...
    # Tier 2: Capability (feature libraries)
    "capability/schemas_embedded",
    ...
    # Tier 3: Gates (PyO3 modules)
    "gates/gate_raw_definition_input",
    ...
]
```

**Current ordering makes it easy to accidentally duplicate or miss entries.** The members list includes entries like `"gates/gate_includes_merged_output"` followed by `"gates/gate_includes_merged_input"` -- note these are not alphabetically adjacent to the other `includes_merged` entries.

## 8. Test Organization

### Current state

All tests use inline `#[cfg(test)] mod tests` within source files. There are zero separate `tests/` directories anywhere in the workspace.

### Assessment

**Inline tests are the correct choice for this workspace.** The crates are small enough that colocating tests with source is natural. No crate has enough test code to justify a separate directory. The pattern is consistent across all 53 files that contain tests.

**No integration tests exist.** The workspace has no `tests/` directories at any level. For most crates this is fine (unit tests suffice), but there are candidates for integration testing:
- The deploy scripts themselves (do they produce working binaries?)
- The hook pipeline (does stdin-to-stdout work end-to-end?)
- Schema embedding (does a schema change propagate correctly after rebuild?)

These are not urgent, but their absence is worth noting.

## 9. Schema Organization

### Current state

```
schemas/
  agents/   -- 20 schema files (13 agent pipeline + 7 include fragments)
  tools/    -- 6 schema files
```

### Assessment

**The agents/tools split is clean and appropriate.** Agent pipeline schemas and tool schemas serve different purposes. The split reflects the domain.

**Schema naming is consistent.** All schema files use kebab-case (the documented exception to underscore-everywhere). The naming pattern maps predictably to crate names: `agent-raw-definition.schema.json` -> `gate_raw_definition_input`.

**One naming inconsistency in tools/:** `validate.datagram.schema.json` uses a dot separator while all other schema files use kebab-case. Every other schema: `qc-report.schema.json`, `glossary.schema.json`, `raw-jsonl.schema.json`. The datagram schema: `validate.datagram.schema.json`. The dot makes this file sort and pattern differently.

**The relationship between schemas/ and schemas_embedded/ is discoverable** because `schemas_embedded/src/lib.rs` uses `include_str!("../../../schemas/...")` paths. An LLM reading the code can trace the connection.

## 11. Naming Consistency

### Naming violations found

1. **`datagram_types` in `core/` lacks `_core` suffix.** Convention: core crates use `_core` suffix. This crate defines pure types (Datagram, DatagramKind, Priority) with no I/O. It is a core crate by every measure except its name. Documented in NORNIR_NAMING.md's core library table but breaks the suffix rule.

2. **`traffic_interceptor_rewriter` violates verb-prefix naming.** Documented as a known exception in NORNIR_NAMING.md. Correct name: `intercept_traffic_rewrite`.

3. **`validate.datagram.schema.json` uses dot separator.** All other schemas use kebab-case. This should be `validate-datagram.schema.json` or just `datagram.schema.json`.

### Naming consistency confirmed

- All 8 `check_*` binaries: directory = package = binary. Verified.
- All 5 `hook_*` binaries: directory = package = binary. Verified.
- All 5 `send_*` binaries: directory = package = binary. Verified.
- All 5 `append_*/write_*` binaries: directory = package = binary. Verified.
- All 33 `gate_*` modules: directory = package. Verified.
- `saga_cli`/`syn_cli` exceptions: documented and correct.
- All `_core` suffix crates in `core/`: verified (except `datagram_types`).
- All capability crates lack `_core` suffix: verified.

## 15. LLM Navigability Summary

### What works well

1. **Category directories are self-documenting.** `hooks/hook_pre_llm_bash/` tells you everything: category, verb, timing, scope.
2. **The core/capability split encodes architecture.** An LLM can determine a crate's tier by its directory.
3. **Design documents are colocated with code.** HOOK_DESIGN.md in hooks/, SYN_DESIGN.md in cli/syn_cli/.
4. **Naming conventions are documented and mostly followed.** NORNIR_NAMING.md is thorough and accurate.

### What causes LLM confusion

1. **Root clutter from deploy scripts.** 12 Python files dilute the signal from documentation.
2. **Six single-member directories look like empty categories.** An LLM may hesitate to add a crate to a "nearly empty" category.
3. **cli/ mixes check tools with specialist tools.** An LLM reading cli/ cannot infer a consistent pattern.
4. **Cargo.toml member ordering is opaque.** An LLM cannot quickly determine if a crate is a member.
5. **PLAN.md reference in NORNIR_ORGANIZATION.md points to a nonexistent file.** An LLM will try to read it and fail.
6. **`datagram_types` breaks the `_core` naming convention.** An LLM may pattern-match on this exception and create more `_types` crates in core/.
7. **Deploy scripts are separated from what they deploy.** An LLM adding a new writer must remember to also update a script at the workspace root.
